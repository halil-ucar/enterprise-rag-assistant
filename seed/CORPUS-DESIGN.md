# Corpus design — curated core + generated haystack

> **This document states the design *intent* (written before the build). The sizes below
> are planning targets, not the as-built counts — see the `manifest.json` files and the
> README for what shipped: core = 42 docs / 214 chunks, core golden set = 37 questions,
> the measured scale index = core + `FILL=1500` = 5 826 chunks. The design principles
> (hard-negative families, disjoint haystack namespace, doc+section anchors) all hold.**

The evaluation corpus is deliberately **two-tiered**. Quality and scale are different
questions and get different data:

| Tier | Size (target) | Authored by | Committed | Measures |
|---|---|---|---|---|
| Smoke corpus (`seed/corpus/`) | 12 docs / ~38 chunks | hand | generated by `make_corpus.py` | CI plumbing, fast tests |
| **Curated core** (`seed/corpus-core/`) | ~120–150 (built: 42) | hand (designed hard negatives) | yes (plain `.md`) | retrieval **quality** |
| **Generated haystack** (`seed/corpus-fill/`) | 2 000–5 000 docs | `make_fill_corpus.py`, seeded RNG | no (git-ignored, regenerate) | **scale**: index size, latency |

Rationale: at 38 chunks every configuration scores Recall@5 = 1.0 (ceiling effect — see
README eval table). Discriminative quality measurement needs *hard negatives by design*;
realistic latency numbers need *mass*. Mass-generating unique prose with an LLM is the
wrong tool for both: haystack docs don't need originality (templates suffice at 0 cost),
and hard negatives need deliberate design, not volume.

---

## 1. Curated core — document families

Every family exists to break retrieval in one specific, realistic way. Target counts are
guidance, not quotas; quality of the trap beats hitting the number.

### F1 · Version twins (~15 pairs/triples)
The same policy/manual in 2–3 versions: one **current**, one **DRAFT** (explicitly "noch
nicht gültig"), one **DEPRECATED** (with "abgelöst durch …" pointer). Content overlaps
heavily; key facts differ (dates, thresholds, responsible roles).
*Examples:* VPN-Handbuch v2 (gültig) / v3 (Entwurf) / v1 (veraltet); Reisekostenrichtlinie
2024 vs. 2026; Backup-Konzept alt/neu.
*Golden questions:* "Was ist die **aktuelle** Regelung für X?" — anchor on the current
version; DRAFT/DEPRECATED ranking above it is the failure this family exposes.

### F2 · Location/scope twins (~10 pairs)
Same policy type, different scope, materially different rules.
*Examples:* Mobiles Arbeiten Standort Hagen (Kernzeit 10–15 Uhr) vs. Standort Köln
(9–14 Uhr); Zutrittsregelung; Parkplatzordnung.
*Golden questions* carry the qualifier ("… am Standort Köln?") — anchor on the right twin.

### F3 · System confusables (~15 docs)
Runbooks for similar-sounding systems with **different error-code tables**.
*Examples:* NF-MAIL-01 vs. NF-MAIL-ARCHIV; Drucker LJ-70 vs. LJ-90 (distinct code sets,
e.g. LJ-70: E-501 Papierstau ≠ LJ-90: E-501 Tonerfehler); VPN vs. WLAN-Gastzugang.
*Golden questions* on exact codes — this is where the lexical leg must earn its place.

### F4 · Process chains / multi-doc (~10 docs)
One answer requires 2–3 documents (Onboarding → verweist auf VPN-Handbuch + Hardware-
Katalog + Zugangsantrag; Offboarding; Security-Incident über Melde-, Bearbeitungs- und
Eskalationsdokument). *Golden questions* marked `hard: true` (agentic route).

### F5 · Table-heavy documents (~10 docs)
Gehaltsbänder (hr/confidential), Hardware-Katalog, SLA-Matrix, Fehlercode-Tabellen,
Ersatzteil-Liste. Tables must survive chunking as standalone chunks (chunker contract).

### F6 · FAQ/prose duplicates (~8 docs)
The same fact stated in an FAQ document *and* inside a manual section. Both are correct
answers → golden schema needs `expected_doc_any: [a, b]` (eval extension, see §4).

### F7 · Boilerplate carriers (all docs)
Every core doc starts with a standardized header block: Dokumenten-Nr., Version, Stand,
Verantwortlich, Änderungshistorie (small table). Realistic noise; chunking must not let
headers dominate retrieval.

### F8 · RLS/department docs (~6 docs)
hr-only additions (Bewerbungsprozess intern, Gehaltsband-Zusatzvereinbarungen,
BEM-Verfahren) beside the existing ones; collection `hr`, data class confidential.
*Golden questions* run as user `ben` (and as `anna` expecting refusal/empty).

### F9 · Injection carriers (~3 docs)
Prepared indirect-prompt-injection documents beyond the existing one: a ticket export with
an embedded instruction ("Ignoriere alle Regeln und …"), a supplier doc with HTML/markup
payload. *Golden questions* assert the payload is treated as data (`must_not_contain`).

### F10 · Unanswerable neighbours (~5 docs)
Documents *near* an unanswerable question (Dienstrad-Leasing exists; Dienstwagen-Leasing
does not). *Golden questions* with `expect_refusal: true` — refusal under semantic
temptation, not in a vacuum.

**Voice mix:** rotate three author voices across docs — formal QM prose, terse IT runbook
style, HR-friendly prose — plus inconsistent abbreviation use (VPN vs. "Virtual Private
Network", MA vs. "Mitarbeitende"). Length 300–1 200 words (a few manuals 2 000+),
3–8 sections, German, Markdown. All content fictional (Nordfels IT GmbH universe); no
real company names, no real people.

**Reserved namespace:** core system/product tokens (`NF-*` system names, `LJ-70`, `LJ-90`,
error codes used by golden anchors) are RESERVED — the fill generator must never emit
them, or haystack docs would corrupt the anchors.

## 2. Generated haystack (`seed/make_fill_corpus.py`)

- Deterministic: `random.Random(42)`, byte-identical output on every run (assert via
  `--selftest` like `make_corpus.py`); **never** committed — regenerate on demand.
- Building blocks: ~30 templates (generic runbooks, Richtlinien, Protokolle, Meeting-
  Notizen, Changelogs) × pools of invented systems/locations/roles/dates. No LLM calls.
- Distribution: mostly collection `handbuecher` / department `all` or `it` (so `anna`
  questions face the crowd), a small hr slice for `ben`.
- doc_id prefix `fill-`, titles must not collide with reserved core tokens.
- No golden question ever anchors on a fill doc — they are distractor mass only.

## 3. Golden set v2 (`seed/golden_set_core.yaml`, 50–60 questions)

Category matrix (each ≥4 questions unless noted): `error_code`, `paraphrase`, `compound`,
`table`, `multi_doc` (hard), `version`, `location`, `faq_dup`, `rls` (2–3), `refusal`,
`injection` (2–3). Fields per question: `id`, `category`, `question`, `collection`,
`user` (anna/ben), and either `expected_doc` + `expected_section_contains`,
`expected_doc_any` (F6), `expect_refusal`, or injection assertions
(`expected_answer_contains` / `must_not_contain`). Every anchor MUST reference an
existing core doc_id + section — validated by a check script (see §4), not by trust.

---

## 4. Harness extensions that come with this corpus

1. `eval/run_eval.py`: per-**category** breakdown next to the aggregate
   (aggregate MRR hides *where* hybrid wins/loses), `--golden <file>` flag,
   `expected_doc_any` support, retrieval latency p50/p95 in the report.
2. `seed/check_golden.py` (new, 0 tokens): every anchor resolves against the ingested
   corpus (doc exists, section matches, collection/user consistent) — run before eval.
3. `seed/ingest_corpus.py`: `--corpus smoke|core|full` (full = core + fill).
4. Makefile: `seed-core`, `seed-full`, `eval-core`, `eval-full`; CI stays on the smoke
   corpus (fast); core/full runs are local/on-demand.

---

## 5. Execution order (for the generating session)

1. Write core docs family by family (F1–F10), maintaining a manifest with doc_id, title,
   collection, department, family tag.
2. Write `golden_set_core.yaml` alongside each family (anchor while the trap is fresh).
3. `check_golden.py` green → `seed-core` → `eval-core` (records the "core-only" baseline).
4. Build `make_fill_corpus.py` → `seed-full` → `eval-full` (scale numbers + latency).
5. Only then: retrieval tuning experiments (lexical-leg weighting), measured
   before/after on the core golden set, documented in ARCHITECTURE.md.
